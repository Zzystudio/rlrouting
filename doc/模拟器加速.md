# 模拟器 GPU 加速方案（2026-09-16）

> 目标：将轨迹噪声模拟器（`sim/trajectory_sim.py` v1 批量内核 + `sim/trajectory_sim_v2.py`
> 事件级模拟器）从 NumPy CPU 移植到 PyTorch CUDA 后端，消除评估与噪声感知训练的
> 最大计算瓶颈。
> 关键定位：模拟器全部内核是**访存受限的批量态矢量运算**——正是 GPU 高带宽的主场；
> 且 CPU 侧 8 MiB 工作集上限使 20q 批量退化为逐轨迹串行，GPU VRAM 可一次性成批。
> 预期端到端收益 **~10-50×**。

---

## 1. 瓶颈定位（代码事实）

| 事实 | 位置 | 含义 |
|------|------|------|
| 全部内核是 NumPy CPU 实现 | `trajectory_sim.py` | 无 GPU 路径（`sim.py:68` 的 `device` 字段只服务 Aer 后端，且 Aer 密度矩阵 4ⁿ 在 20q = 16 TB，物理不可用） |
| 工作集上限 8 MiB | `trajectory_sim.py:836` `_BATCH_WS_LIMIT` | **20q 单条轨迹 = 2²⁰×16B = 16 MiB > 8 MiB → chunk=max(1,…)=1，批量退化为逐轨迹串行**（CPU L3 缓存调优的副作用） |
| 内核全部是访存受限操作 | `_apply1_batch`（strided 视图+线性组合）、`_apply_cx_batch`（全数组 copy）、`_apply_swap_batch`（转置）、`_thermal_noise_batch`（bool 索引+归约）、`_depol2_batch`（15 类 Pauli 分支索引）、`_zz_rotation_batch`（xor 索引相位乘） | 带宽比 GPU ~10-20× CPU，同类负载迁移收益直接 |
| 动作流编译是纯 Python 一次性工作 | `_prepare_events`（校验/排序/串扰对检测/空闲区间求交） | 留在 CPU，成本可忽略，不动 |

**关键洞察——GPU 收益是双重的**：
1. 带宽比（~20×）；
2. VRAM（GiB 级）取代 L3（8 MiB）作工作集上限后，T=16-64 条轨迹**真正成批**
   （20q×T=64 = 1 GiB，≥8 GB 卡轻松装下），消除逐轨迹 chunk 循环。

粗算：20q、T=64、500 门路由后电路（~1500 动作含噪声子操作）：
- CPU 现状：64 chunk × 每动作 ~4 遍 × 16 MiB ≈ 6 TB 总访存 @ ~40 GB/s 有效带宽 → ~百秒级/电路；
- GPU：同总访存量（T=64 成批后每动作 ~4 GiB）@ ~800 GB/s → **~个位数秒/电路**。

---

## 2. 方案选型

| 选项 | 评估 | 结论 |
|------|------|------|
| **PyTorch CUDA** | 已是项目依赖；v1/v2 内核集相同，移植一处两版继承；complex128 CUDA 支持完整 | ✅ **推荐** |
| CuPy | drop-in 替换最省事，但引入新依赖，且 torch 已能做全部所需操作 | 备选 |
| qiskit-aer GPU | 密度矩阵 4ⁿ 内存爆炸（轨迹 MC 正是为绕开它而存在） | ❌ 仅 ≤12q 的 aer 口径受益，非主战场 |

**FP64 顾虑不成立**：内核访存受限而非计算受限，消费级卡的弱 FP64 算力无关紧要；
可选 `complex64` 模式再省一半带宽（见 §5-P5）。

---

## 3. 架构设计

### 3.1 内核级移植（v1/v2 一次到位）

v2（`EventTrajectorySimulator`）继承 v1 的 8 个批量内核
（`_apply1/_apply_cx/_apply_swap/_thermal_noise/_depol1/_depol2_batch` + `_zz_xor_indices`），
v2 自加 2 个（`_apply_cz_batch`、`_zz_rotation_batch`）。
**在内核层做设备分派，v1/v2 同时获得 GPU 支持**：

```python
# trajectory_sim.py（示意）
def __init__(..., backend: str = "auto"):   # auto/cpu/cuda
    self._device = _pick_device(backend)     # torch.device
    self._use_gpu = self._device.type == "cuda"
```

- 状态 `(T, 2ⁿ)` 以 torch complex128 张量**全程驻留 GPU**：初态上传一次 → 整个
  动作流在 GPU 上跑完 → 只把 fidelity 标量取回 host；
- 内核 torch 化（语义逐行对应）：reshape/strided 视图（torch 同语义）、
  `svs[:, idx] *= phase`、`a0[jump] = a1[jump]` 布尔索引、按 T 轴归约——全部有直接对应；
- `_zz_xor_indices`：`_all = arange(2ⁿ, device=cuda)` 每 n 预计算一次，xor 掩码在
  GPU 上生成（消掉每对 (q1,q2) 的 CPU `np.nonzero` + 上传开销）；
- 动作流编译（`_prepare_events`）保持 CPU/Python 不变，输出轻量动作列表，演化循环
  顺序发射 GPU kernel（~1500 动作 × ~15 μs 发射开销 ≈ 20 ms，可忽略）；
- `_reduce_phys_circuit_for_fidelity_v2`（比特子集缩减）与事件构建全部不动（纯 CPU）。

### 3.2 工作集上限改为 VRAM 驱动

```python
# 替代 _BATCH_WS_LIMIT = 8 MiB（CPU L3 调优）
chunk = max(1, int(0.25 * torch.cuda.mem_get_info()[0]) // ws_traj)
```

按空闲 VRAM 的 25% 切块（默认值，可配）：20q×T=64（1 GiB）在 ≥8 GB 卡上一批装完。

### 3.3 RNG 语义变化（必须正视）

`self.rng = np.random.default_rng(seed)` 的流与 torch CUDA generator **不可能逐位一致**。

| 路径 | 等价性要求 |
|------|-----------|
| 理想/无噪声（`apply_noise=False`） | 纯确定论运算，CPU/GPU **1e-12 级一致**（complex128） |
| 噪声路径（MC Kraus 采样） | **统计等价**：同电路大 T 下均值落在 MC 容差内 |

这是正确的验收口径——fidelity 本来就是统计估计量；但报告中须注明 backend
（所有历史数据均为 CPU 口径）。

## 4. 验收协议（等价性测试）

| 层级 | 测试 | 判据 |
|------|------|------|
| 内核级 | 每个批量内核：随机态输入，CPU vs GPU 输出对比（complex128） | `allclose(1e-12)`（确定论部分逐位级） |
| 演化级 | 无噪声全电路演化 CPU vs GPU | `<1e-12` |
| 统计级 | 同电路 T=1024 噪声轨迹，CPU vs GPU 平均 fidelity | 差值 < 3σ/√T |
| 端到端 | NAM 抽 5 条电路，GPU vs CPU fidelity | 各电路差值在 MC 容差内 |

全部纳入 `test/`，随 `pytest test/ -q` 回归。

## 6. 收益预估与受益面

**端到端 ~10-50×**（带宽比 ~20× × 批量化消除 chunk 循环；kernel launch 开销可忽略）。

受益面按时间顺序：

1. **v1（beam lookahead）M4 评估**：NAM 混合精度 T=64/32/16，≥15q 段 T=64——
   19 电路 × 多口径 × 多次复核，eval 墙钟直接砍一个量级，T=128 复核变便宜；
2. **v3 噪声阶段训练**：`fidelity_fn` 每 episode 终端调用，此前是 v3 最大可预见瓶颈；
3. 所有 `trajectory / trajectory_sched / trajectory_v2` 口径的历史评估脚本。

**与 v1 主线的关系**：v1 训练本身是 routing 模式（无 fidelity_fn），GPU 加速不阻塞
M1-M3；P0（驱动修复）不依赖任何代码改动，可随时先行。

## 7. 风险与决策记录

| 风险 | 缓解 |
|------|------|
| 驱动修复需要 host 权限/重启 | P0 先行验证；若短期修不好，方案整体降级为"代码就绪、待硬件" |
| 统计等价而非逐位等价引入评估口径争议 | §4 协议固定容差；报告中注明 backend，历史数据均为 CPU 口径 |
| complex64 精度争议 | 默认 complex128 不变；complex64 仅作可选加速模式，单独验证后才允许用于评估 |
| VRAM 不足（更大 n 或 T） | chunk 按 `mem_get_info` 动态切块，天然退化安全 |
| torch 索引语义与 NumPy 细微差异（如 bool 索引赋值顺序） | 内核级单测逐个覆盖（§4 第一行） |

**决策记录（2026-09-16）**：

| 决策项 | 定稿 | 说明 |
|--------|------|------|
| 后端 | PyTorch CUDA | 项目已有依赖；v1/v2 一次继承 |
| 实施时机 | 与 v1 beam-lookahead M1 并行 | 改动文件与 beam lookahead 几乎不重叠；M4 评估直接受益 |
| 默认精度 | complex128 | complex64 留作 P5，128 验证通过后作为低风险增量 |
| 工作集策略 | 空闲 VRAM 25% 动态切块 | 替代 8 MiB CPU L3 常数 |

---

## 8. 一句话总结

轨迹模拟器的全部成本都在访存受限的批量态矢量内核上，而 8 MiB 的 CPU 缓存上限已把
20q 批量退化成逐轨迹串行——把 8 个批量内核 torch 化、状态常驻 GPU、VRAM 动态切块，
v1/v2 两版模拟器一次继承，评估与 v3 噪声训练的墙钟预计缩短 10-50×；无噪声路径逐位
等价、噪声路径统计等价，验收协议分层固定容差。

## 9. 实施记录（2026-09-16 完成 P0-P4）

**状态：P0-P4 全部完成**（P5 可选项未做）。实验记录详见 `doc/train.md` 同名章节。

### 实施落点（与 §3/§5 的差异）

| 项 | 方案 → 实际 |
|----|------------|
| simulator 默认 backend | 草案 `auto` → **`cpu`**（历史调用点零感知、全部旧测试不变的更安全选择；auto 上移到 factory 层） |
| auto 语义 | "CUDA 可用即 GPU" → **按工作集分流**：`T×2^n×16B ≥ 128 MiB` 才走 GPU（基准实测小工作集 GPU 反而慢，见下） |
| thermal 内核 | 逐行移植 → **无同步 branchless**（`jump.any()`/bool 索引在 GPU 强制 device 同步，改 where 掩码全数组运算） |
| RNG | torch Generator 独立流，无噪声路径逐位一致（实测 diff=0）、噪声路径统计等价 ✅ |

### 实测基准（真实 NAM 路由电路 × tianyan287_20q，seed=42）

| 电路 | q | T | 工作集 | CPU | GPU | 加速比 |
|------|---|---|--------|-----|-----|--------|
| gf2^6_mult | 18 | 64 | 256 MiB | 2368.0s | 70.7s | **33.5×** |
| tof_10 | 19 | 128 | 1 GiB | 1655.2s | 47.6s | **34.8×** |
| vbe_adder_3 | 10 | 32 | 0.5 MiB | 0.21s | 0.33s | 0.6× |
| tof_5 | 9 | 16 | 8 MiB | 0.04s | 0.17s | 0.2× |

- 深电路加速 ~34×，落在 §6 预估的 10-50× 区间；19q×T=128 复核从 ~28 min → <1 min；
- 小电路 GPU 反而慢 2-5× → auto 阈值分流后混合精度评估两全（≤14q 走 CPU、≥18q 走 GPU）；
- 验收：`test/test_sim_gpu.py` 29 项全绿（内核级 1e-12 / 演化级逐位一致 / 统计级 3σ 容差），
  全量回归 126 passed。
